# 击球时刻和击球人（第 6 步原型）

结论：`badminton hits` 用「球轨迹转折 + 手腕速度」找出每一拍的时刻和击球人。在 `data/singles.mp4`（转播单打，72 秒，66 拍对照）上，误差 ±0.1 秒（3 帧）以内算对，F1 是 91.3%，击球人 57/58 正确。击球声实测帮不上忙，已经去掉。手机录像上还没有对照标注，准确率给不出数字，这是下一步要补的。

| 方法（singles.mp4，66 拍，±3 帧） | 准确率 | 召回率 | F1 | 击球人 |
| --- | --- | --- | --- | --- |
| 球轨迹 + 手腕（默认） | 95.1% | 87.9% | 91.3% | 57/58 |
| 只用球轨迹（`--no-wrist`） | 98.0% | 74.2% | 84.5% | 46/49 |
| BST 试跑里的简单办法（`bst.find_hits`） | 90.6% | 72.7% | 80.7% | 47/48 |

把容许误差放宽到 ±0.2 秒（6 帧，COURTSIDE 用的口径），默认方法是 F1 92.9%。对上的 59 拍里，81% 的时刻误差在 1 帧以内，95% 在 2 帧以内。BST 对击球帧敏感（差 3 帧约 20% 的类型会变），所以主口径用 ±3 帧。

这些数字有三个限制：

- 参数是在这同一段视频上调的，所以偏乐观。调参时看过一遍参数网格（162 组），F1 的中位数是 91%，说明不是靠某一组凑出来的，但换一段视频仍然可能掉几个点。
- 对照是我（Claude）逐帧看放大画面标的，不是人标的。每个候选时刻看前后 7 帧，再用「网两边轮流击球」核对有没有漏。时刻本身有 1–2 帧的不确定。
- 只有一段转播画面。目标是 200–300 拍，现在只有 66 拍。手机录像的画面太糊，我看图分不清有没有碰到球，没有硬标。

## 怎么跑

```bash
badminton skeleton data/singles.mp4 --court data/singles.court.json --singles --stride 1
```

```bash
badminton shuttle data/singles.mp4 --court data/singles.court.json
```

```bash
badminton hits data/singles.mp4 --court data/singles.court.json --singles --labels labels/hits/singles.hits.csv
```

骨架要加 `--stride 1` 逐帧跑：默认每 2 帧一次，手腕速度的峰值会被抹平。球轨迹要加 `--court`，用改进的选点（去掉静止干扰点）。

输出三个文件：

| 文件 | 内容 |
| --- | --- |
| `singles.hits.json` | 每一拍的帧号、时间、击球人、依据的信号、球的位置；每个数值带来源标记 |
| `singles.hits.csv` | 每拍一行：`frame, time_s, player, side, found_by, source`。`scripts/bst_trial.py --hits` 可以直接读 |
| `singles.hits.html` | 逐拍核对页面，见下面「人工核对」 |

## 做法

动工前读了两个项目的事件识别，只借鉴想法，没有拿代码：

- [COURTSIDE](https://github.com/jayclim/BadmintonAI)（`hits.py`，MIT）：击球分数取「速度变化量」和「方向转折」里大的那个；轨迹断开处、发球各有一遍单独的规则；用手腕速度峰值找回球轨迹漏掉的击球。它在 4 场转播单打上击球检测 F1 是 87–89%（±6 帧）。
- [BadmintonTrackNet](https://github.com/ZSHYC/BadmintonTrackNet)（`docs/events`，MIT）：先用运动学规则出高召回的候选（速度反转、加速度峰值），再用一个小分类器（BounceNet）分成击球、落地、都不是；速度按帧率折算。

这里的做法分三步。

**1. 找候选时刻。** 三种来源：

- 球轨迹的转折：取每一帧前后各 0.13 秒的速度，分数是「速度变化量」和「方向转折」里大的那个。前后两段都必须真的在飞，否则高远球顶点、网前翻滚、落地都会被当成转折。轨迹短暂断开时，用断开前后的飞行方向比较。
- 轨迹在球员手边开始或结束：发球之前没有飞行，挥拍时球常常被身体挡住或糊掉，这两种情况算不出转折，但「球从手边冒出来」本身就是信号。
- 手腕速度峰值，而且球在这个人够得着的范围内。

**2. 给每个候选、每个球员打分。** 分数 = 转折强度 + 手腕速度 − 球到手腕的距离 − 一个固定门槛。球离所有人都远的转折是落地或者跟踪错误，直接排除。

**3. 选出总分最高的一组击球，要求同一回合里网两边轮流击球。** 挥拍的余势和下一拍的准备动作，也是「手腕很快、球在手边」，单看一个时刻分不出来；但同一边不可能连打两拍。两拍离得很近（0.6 秒内）时这条是硬性的，离得远时只扣分（说明中间漏了对方一拍），这样漏一拍不会连带后面全错。这条规则对双打同样成立。

和两个参考项目不同的地方：所有阈值都用「离球最近的球员的身高」做单位，不用像素和帧。同样一拍，远端球员那边球在画面上移动的像素只有近端的一半多；按像素定阈值，远端的轻球就会漏（COURTSIDE 自己统计 86–89% 的漏检在远端或发球）。换算以后一套阈值可以用于近端和远端、30 和 60 fps、1080p 和 4K。

还漏的 8 拍：3 拍是发球（球轨迹在发球前后是断的），3 拍在球轨迹丢失的时段里，2 拍是远端的轻球。多出来的 3 拍：2 拍是球落在球员脚边，1 拍时刻偏了 4 帧。

## 击球声：实测后去掉

计划里把击球声列为第三种信号，前提是先实测。做法：取 2–9 kHz 频段的能量，看它在几毫秒内上升了多少（上升 9 dB 记为强度 1），再看击球时刻有没有这样的「声音起点」。

在两段手机录像（`IMG_8923`、`jay_cdl`，都是有隔壁场地的球馆）上，用程序识别出的击球做对比：

| | IMG_8923 | jay_cdl |
| --- | --- | --- |
| 击球时刻 ±1 帧内有明显的声音起点 | 22.7% | 20.0% |
| 随机时刻 ±1 帧内有明显的声音起点 | 11.0% | 9.5% |
| 回合内明显的声音起点里，能对上某次击球的 | 32 / 144 | 32 / 137 |

换过 135 种频段、窗长和算法的组合，最好的也只是「四到五成的击球对得上，随机时刻两成左右」。也就是说，一半以上的击球听不出来，而四分之三的声音起点是别的声音（隔壁场地、脚步、喊声）。它既不能确认一个候选，也不能否定一个候选，所以没有接进 `badminton hits`。

这个结论有一个保留：对比用的是程序识别出的击球，不是人工对照；手机录像上球轨迹只有六七成正确，真实的对上比例可能更高一些。测量脚本留在 `scripts/hit_sound_probe.py`，有了人工核对过的击球以后可以重跑：

```bash
python scripts/hit_sound_probe.py data/IMG_8923_stab.mp4 --hits IMG_8923_stab.hits.labels.csv --rallies IMG_8923_stab.movement.json
```

## 人工核对

`badminton hits` 每次都会写一个 `<视频名>.hits.html`。用浏览器打开，选同一个视频文件，就可以逐拍核对：

- 空格慢放这一拍前后，回车确认，X 表示不是击球；
- 左右方向键把时刻挪一帧，数字键 1–4 改击球人；
- A 在当前画面加一拍（程序漏掉的）；
- S 导出 `<视频名>.hits.labels.csv`（`Frame, Player, Note`）。

导出的文件有两个用处：

```bash
badminton hits match.mp4 --court match.court.json --labels match.hits.labels.csv
```

报告准确率、召回率和 F1。

```bash
badminton hits match.mp4 --court match.court.json --manual match.hits.labels.csv
```

不做识别，直接把核对过的结果写成击球文件，来源标记是「人工」。

`Note` 列写 `ignore` 的行不计入对错（比如死球时间里把球挑给对方、视频结尾被截断的一拍）。`labels/hits/singles.hits.csv` 是 singles.mp4 的对照。

这个页面还没有在浏览器里实际操作验证过，只测了文件能正确生成。

## 数据来源标记

每个数值带一个来源，一共四种，定义在 `src/badminton/provenance.py`：

| 标记 | 含义 |
| --- | --- |
| `measured` 实测 | 模型在这一帧直接检测到的 |
| `interpolated` 插值 | 短暂丢失后补出来的 |
| `derived` 推算 | 用几何或运动规律算出来的 |
| `manual` 人工 | 人工标注或确认的 |

现在各个文件里的标记：

| 文件 | 标记方式 |
| --- | --- |
| `*.shuttle.csv` | 新增第 5 列 `Source`：TrackNet 在这一帧看到球是 `measured`；InpaintNet 补的、选点后补的短缺口、隔帧推理时中间的帧是 `interpolated` |
| `*.hits.json` | 帧号和时间是 `derived`（人工核对过的是 `manual`）；球的位置沿用球轨迹那一帧的标记；击球人是 `derived`，另外注明手腕关节点在这一帧是实测还是插值 |
| `*.movement.json` | 每个球员新增 `position_sources`：回合内的位置有多大比例是实测、多大比例是插值（腾空、漏检时补的）；顶层新增 `sources`，说明距离、速度、冲刺次数等都是 `derived`，名字是 `manual` |
| `*.labels.csv`（球的标注） | 已有的 `Status` 列：`machine` 读成 `measured`，其余读成 `manual` |

旧的 `*.shuttle.csv` 没有 `Source` 列，读的时候一律当成 `measured`；读这个文件的其他命令不受多出来的一列影响。骨架文件（`.skeleton.npz`）里存的都是模型跑过的帧，全部是实测，没有加标记。

AI 点评那一步还没有读这些标记。按计划，对插值和推算出来的数字，大模型不应该下确定的结论，这要在点评的提示词里接上。
