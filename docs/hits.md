# 击球时刻和击球人（第 6 步原型）

结论：`badminton hits` 用「球轨迹转折 + 手腕速度」找出每一拍的时刻和击球人。在 `data/singles.mp4`（转播单打，72 秒，66 拍对照）上，误差 ±0.1 秒（3 帧）以内算对，F1 是 91.3%，击球人 57/58 正确。击球声实测帮不上忙，已经去掉。手机录像上还没有对照标注，准确率给不出数字，这是下一步要补的。在 7 场职业男双转播（BFMD，5239 拍人工标注）上，±3 帧 F1 是 79.8%，±6 帧是 86.8%，见「BFMD 职业双打对照」。

| 方法（singles.mp4，66 拍，±3 帧） | 准确率 | 召回率 | F1 | 击球人 |
| --- | --- | --- | --- | --- |
| 球轨迹 + 手腕（默认） | 95.1% | 87.9% | 91.3% | 57/58 |
| 只用球轨迹（`--no-wrist`） | 98.0% | 74.2% | 84.5% | 46/49 |
| BST 试跑里的简单办法（`bst.find_hits`） | 90.6% | 72.7% | 80.7% | 47/48 |

把容许误差放宽到 ±0.2 秒（6 帧，COURTSIDE 用的口径），默认方法是 F1 92.9%。对上的 59 拍里，81% 的时刻误差在 1 帧以内，95% 在 2 帧以内。BST 对击球帧敏感（差 3 帧约 20% 的类型会变），所以主口径用 ±3 帧。

这些数字有三个限制：

- 参数是在这同一段视频上调的，所以偏乐观。调参时看过一遍参数网格（162 组），F1 的中位数是 91%，说明不是靠某一组凑出来的，但换一段视频仍然可能掉几个点。
- 对照是我（Claude）逐帧看放大画面标的，不是人标的。每个候选时刻看前后 7 帧，再用「网两边轮流击球」核对有没有漏。时刻本身有 1–2 帧的不确定。
- 只有一段转播画面。目标是 200–300 拍，现在只有 66 拍。手机录像的画面太糊，我看图分不清有没有碰到球，没有硬标。

## 做法

动工前读了两个项目的事件识别，只借鉴想法，没有拿代码：

- [COURTSIDE](https://github.com/jayclim/BadmintonAI)（`hits.py`，MIT）：击球分数取「速度变化量」和「方向转折」里大的那个；轨迹断开处、发球各有一遍单独的规则；用手腕速度峰值找回球轨迹漏掉的击球。它在 4 场转播单打上击球检测 F1 是 87–89%（±6 帧）。
- [BadmintonTrackNet](https://github.com/ZSHYC/BadmintonTrackNet)（`docs/events`，MIT）：先用运动学规则出高召回的候选（速度反转、加速度峰值），再用一个小分类器（BounceNet）分成击球、落地、都不是；速度按帧率折算。

这里的做法分三步。

**1. 找候选时刻。** 三种来源：

- 球轨迹的转折：取每一帧前后各 0.13 秒的速度，分数是「速度变化量」和「方向转折」里大的那个。前后两段都必须真的在飞，否则高远球顶点、网前翻滚、落地都会被当成转折。轨迹短暂断开时，用断开前后的飞行方向比较。
- 轨迹在球员手边开始或结束：发球之前没有飞行，挥拍时球常常被身体挡住或糊掉，这两种情况算不出转折，但「球从手边冒出来」本身就是信号。
- 手腕速度峰值，而且球在这个人够得着的范围内。

**2. 给每个候选、每个球员打分。** 分数 = 转折强度 + 手腕速度 − 球到手腕的距离 − 一个固定门槛。球离所有人都远的转折是落地或者跟踪错误，直接排除。

**3. 选出总分最高的一组击球，要求同一回合里网两边轮流击球。** 挥拍的余势和下一拍的准备动作，也是「手腕很快、球在手边」，单看一个时刻分不出来；但同一边不可能连打两拍。两拍离得很近（0.6 秒内）时这条是硬性的，离得远时只扣分（说明中间漏了对方一拍），这样漏一拍不会连带后面全错。这条规则对双打同样成立。

**4. 去掉孤立的一拍。** 前后 2.5 秒（`RALLY_GAP_S`）内都没有别的击球的那一拍丢掉（`drop_lone_hits`，在 `run` 里、选完之后做，不影响打分和选择）。回合之间捡球、接住球、把球拨回给发球的人，看起来都是「球从手边飞出去」或「飞到手里」，和发球、击球一样；区别是没人回球，这个「回合」只有一拍。代价是真正只有一拍的回合（发球直接得分、发球下网）也会丢，这种情况很少。

实测（2026-11-14）：singles.mp4 不变（±3 帧 F1 89.6%）；BFMD 7 场 ±3 帧 F1 79.8% → 79.9%（多检 944 → 913，对的 4105 → 4090），±6 帧 86.8% 不变；IMG_0971（手机双打，用微调后的球追踪）去掉了第一回合结束后的捡球（880 帧）和接球（1030 帧），其他击球不变。也试过「回合首尾证据弱的一拍也去掉」：BFMD ±3 帧略升，但 ±6 帧和 singles 都下降，没有采用。

和两个参考项目不同的地方：所有阈值都用「离球最近的球员的身高」做单位，不用像素和帧。同样一拍，远端球员那边球在画面上移动的像素只有近端的一半多；按像素定阈值，远端的轻球就会漏（COURTSIDE 自己统计 86–89% 的漏检在远端或发球）。换算以后一套阈值可以用于近端和远端、30 和 60 fps、1080p 和 4K。

还漏的 8 拍：3 拍是发球（球轨迹在发球前后是断的），3 拍在球轨迹丢失的时段里，2 拍是远端的轻球。多出来的 3 拍：2 拍是球落在球员脚边，1 拍时刻偏了 4 帧。

## 击球声：实测后去掉

计划里把击球声列为第三种信号，前提是先实测。做法：取 2–9 kHz 频段的能量，看它在几毫秒内上升了多少（上升 9 dB 记为强度 1），再看击球时刻有没有这样的「声音起点」。

在两段手机录像（`IMG_8923`、`jay_cdl`，都是有隔壁场地的球馆）上，用程序识别出的击球做对比：

| | IMG_8923 | jay_cdl |
| --- | --- | --- |
| 击球时刻 ±1 帧内有明显的声音起点 | 22.7% | 20.0% |
| 随机时刻 ±1 帧内有明显的声音起点 | 11.0% | 9.5% |
| 回合内明显的声音起点里，能对上某次击球的 | 32 / 144 | 32 / 137 |

换过 135 种频段、窗长和算法的组合，最好的也只是「四到五成的击球对得上，随机时刻两成左右」。也就是说，一半以上的击球听不出来，而四分之三的声音起点是别的声音（隔壁场地、脚步、喊声）。它既不能确认一个候选，也不能否定一个候选，所以没有接进 `badminton hits`。

这个结论有一个保留：对比用的是程序识别出的击球，不是人工对照；手机录像上球轨迹只有六七成正确，真实的对上比例可能更高一些。测量脚本留在 `scripts/hit_sound_probe.py`，有了人工核对过的击球以后可以重跑：

```bash
python scripts/hit_sound_probe.py data/IMG_8923_stab.mp4 --hits IMG_8923_stab.hits.labels.csv --rallies IMG_8923_stab.movement.json
```

## 人工核对

`badminton hits` 每次都会写一个 `<视频名>.hits.html`。用浏览器打开，选同一个视频文件，就可以逐拍核对：

- 空格慢放这一拍前后，回车确认，X 表示不是击球；
- 左右方向键把时刻挪一帧，数字键 1–4 改击球人；
- A 在当前画面加一拍（程序漏掉的）；
- S 导出 `<视频名>.hits.labels.csv`（`Frame, Player, Note`）。

导出的文件有两个用处：

```bash
badminton hits match.mp4 --court match.court.json --labels match.hits.labels.csv
```

报告准确率、召回率和 F1。

```bash
badminton hits match.mp4 --court match.court.json --manual match.hits.labels.csv
```

不做识别，直接把核对过的结果写成击球文件，来源标记是「人工」。

`Note` 列写 `ignore` 的行不计入对错（比如死球时间里把球挑给对方、视频结尾被截断的一拍）。`labels/hits/singles.hits.csv` 是 singles.mp4 的对照。

这个页面还没有在浏览器里实际操作验证过，只测了文件能正确生成。

## 数据来源标记

每个数值带一个来源，一共四种，定义在 `src/badminton/provenance.py`：

| 标记 | 含义 |
| --- | --- |
| `measured` 实测 | 模型在这一帧直接检测到的 |
| `interpolated` 插值 | 短暂丢失后补出来的 |
| `derived` 推算 | 用几何或运动规律算出来的 |
| `manual` 人工 | 人工标注或确认的 |

现在各个文件里的标记：

| 文件 | 标记方式 |
| --- | --- |
| `*.shuttle.csv` | 新增第 5 列 `Source`：TrackNet 在这一帧看到球是 `measured`；InpaintNet 补的、选点后补的短缺口、隔帧推理时中间的帧是 `interpolated` |
| `*.hits.json` | 帧号和时间是 `derived`（人工核对过的是 `manual`）；球的位置沿用球轨迹那一帧的标记；击球人是 `derived`，另外注明手腕关节点在这一帧是实测还是插值 |
| `*.movement.json` | 每个球员新增 `position_sources`：回合内的位置有多大比例是实测、多大比例是插值（腾空、漏检时补的）；顶层新增 `sources`，说明距离、速度、冲刺次数等都是 `derived`，名字是 `manual` |
| `*.labels.csv`（球的标注） | 已有的 `Status` 列：`machine` 读成 `measured`，其余读成 `manual` |

旧的 `*.shuttle.csv` 没有 `Source` 列，读的时候一律当成 `measured`；读这个文件的其他命令不受多出来的一列影响。骨架文件（`.skeleton.npz`）里存的都是模型跑过的帧，全部是实测，没有加标记。

AI 点评那一步还没有读这些标记。按计划，对插值和推算出来的数字，大模型不应该下确定的结论，这要在点评的提示词里接上。

### 数据和做法

- 数据：BFMD 数据集的 `hits_doubles/`，是 Label Studio 时间线导出。`hit` 是单帧，`Rally` 是回合区间，另外还有 `bounce`（落地）、`net_hit`（擦网）、`replay`（回放）等。视频用 yt-dlp 从 YouTube 下载（≤720p，合并成 mp4），7 场的时长和 BFMD 列表里的 `youtube_duration_s` 都一致，都是 1280×720、30 fps。数据和视频放在仓库外（`~/codebase/datasets/`），没有提交。BFMD 自带的下载和可视化脚本没有运行。
- 只取回合：转播里大半时间是回放、特写和局间休息，所以只处理 `Rally` 区间。`scripts/bfmd_hits.py clip` 把每个回合前后各多留 15 帧，拼成一个视频；回合之间把最后一帧定格 80 帧。定格的画面里人不动，球的位置不变，会被 `drop_static` 去掉；停顿也长于 `RALLY_GAP_S`，下一回合会重新开始算「两边轮流击球」。另外写一张帧号对照表，打分时把识别结果换回整场视频的帧号。只算落在回合区间里（前后放宽 6 帧）的识别结果，只算回合区间里的标注（5450 拍里有 5239 拍在回合内；有一场有 103 拍落在没标回合的时段里）。
- 每场：`calibrate --auto`（7 场置信度 95–98%，都看过预览图）→ `skeleton --stride 1`（双打，每边 2 人）和 `shuttle --court` 同时跑 → `hits`（不加 `--singles`）。

```bash
python scripts/bfmd_hits.py labels BFMD/annotations/hits_doubles/<比赛>.json -o eval/
python scripts/bfmd_hits.py clip videos_doubles/<比赛>.mp4 --rallies eval/<比赛>.rallies.json -o eval/<比赛>/<比赛>.rallies.mp4
badminton calibrate eval/<比赛>/<比赛>.rallies.mp4 --auto --time 20
badminton skeleton eval/<比赛>/<比赛>.rallies.mp4 --court eval/<比赛>/<比赛>.rallies.court.json --stride 1
badminton shuttle eval/<比赛>/<比赛>.rallies.mp4 --court eval/<比赛>/<比赛>.rallies.court.json
badminton hits eval/<比赛>/<比赛>.rallies.mp4 --court eval/<比赛>/<比赛>.rallies.court.json --labels eval/<比赛>/<比赛>.rallies.labels.csv
python scripts/bfmd_hits.py score eval/*/*.rallies.mp4 --shift -1
```

`badminton hits --labels` 直接读片段帧号的对照，报告的是没有减 1 的数字；`score` 汇总 7 场，并且可以平移标注。

耗时（M5）：下载 7 场 4.4 GB 约 12 分钟；切片每场 1–2 分钟；标定每场 4 秒；骨架和球轨迹同时跑，每场 12–22 分钟（骨架约 31 帧/秒是瓶颈，球轨迹约 70 帧/秒）；`hits` 每场 20 秒。7 场回合内共 13.0 万帧（含定格），全部跑完约 2 小时。

### 帧号对齐

BFMD 的说明写着单打帧号已在 2026-07-10 从 Label Studio 的「从 1 开始」改成「从 0 开始」，双打没有说明。核对办法：在每个标注的击球前后各 8 帧，对球轨迹做「两段直线」拟合，找出最合适的折点（只用球轨迹，不经过击球识别的打分和选择）。

| | 有明显折点的拍数 | 折点减标注帧：平均 | 中位数 | 最多的 |
| --- | --- | --- | --- | --- |
| singles.mp4（逐帧看图标的接触帧） | 52 / 66 | −0.44 | 0 | 0 |
| BFMD 7 场，每场 | 365–733 / 场 | −1.30 到 −1.46 | −1 到 −2 | −1 或 −2 |

7 场的偏移一致，比 singles 的对照多出约 1 帧：BFMD 双打标的帧比球真正转折晚约 1 帧。最可能的原因是双打标注还是 Label Studio「从 1 开始」的帧号，没有像单打那样改过；也可能标注习惯是「看到球已经弹开的第一帧」。两种情况的处理方法一样：把标注减 1 帧，和我们「接触帧」的口径对齐。没有减 2：减 2 帧的 F1 还能再高 1–2 个点，但那等于按识别结果去凑标注，独立证据只支持 1 帧。

减 1 帧以后，对上的击球里识别仍然平均早 0.95 帧（中位数 −1），63% 在 1 帧以内，88% 在 2 帧以内。singles 上是 81% 在 1 帧以内，所以双打转播上击球时刻本身也偏粗一些。

抽帧看图的直接核对没有给出确定结论：720p 转播里球只有几个像素，击球前后几帧的拍子和球都是糊的，分不出 1 帧的差别。所以上面的结论来自轨迹拟合，不是来自看图。

### 漏检和误检的原因

按规则粗分（`scripts/bfmd_hit_causes.py`）。每个漏检或误检按下面的顺序取第一个符合的原因。±3 帧口径下：

| 漏检（共 1134） | 拍数 | 占比 |
| --- | --- | --- |
| 识别到了，但时刻偏 4–8 帧 | 471 | 42% |
| 远端（球在、有轨迹，靠近远端球员） | 219 | 19% |
| 多人挨着球（两人以上的框都靠着球） | 166 | 15% |
| 发球（回合第一拍） | 108 | 10% |
| 球轨迹丢失（前后 7 帧里看到球 ≤ 2 帧） | 101 | 9% |
| 回合中途换机位或切镜头 | 48 | 4% |
| 近端、网前及其他 | 21 | 2% |

| 误检（共 944） | 拍数 | 占比 |
| --- | --- | --- |
| 时刻偏 4–8 帧（和上面的漏检成对） | 458 | 49% |
| 落地或出界被当成击球（6 帧内有 BFMD 的 bounce 标签） | 187 | 20% |
| 其他：挥拍没碰到球、轨迹跟错点 | 123 | 13% |
| 回合结束后（捡球、收拍、把球打回去） | 98 | 10% |
| 擦网或下网（6 帧内有 net_hit 标签） | 55 | 6% |
| 换机位、发球前 | 23 | 2% |

几点观察：

- **最大的一类是时刻偏 4–8 帧，不是没找到。** 这类在 ±3 帧口径下同时算一次漏检和一次误检，放宽到 ±6 帧大部分就对上了，这就是 ±3 帧和 ±6 帧差 7 个点的原因。偏的方向两边都有，往前偏的多（−4 帧最多）。可能的原因：双打里球离击球人身体近，转折处常常被身体挡住；离球近的手腕不止一只，手腕速度峰值会把时刻往挥拍开始的地方拉。
- **远端比近端难得多。** 剩下的漏检里远端 219 拍，近端只有 18 拍。和 singles、手机录像上的结论一样：远端球员在 720p 转播里约 100 像素高，球的位移和手腕都小。
- **四人挤在一起** 是双打特有的问题，占漏检的 15%：网前封网、前后站位交换时，「同一边不能连打两拍」这条规则分不清是谁打的，还会把队友的挥拍当成击球。
- **落地被当成击球** 是最大的一类真误检。落地点常在球员脚边，满足「离手腕不远」；BFMD 正好标了 bounce，以后可以拿来训练一个小分类器（击球 / 落地 / 都不是），就是 BadmintonTrackNet 的 BounceNet 那种做法。

抽查：在第 1 场里每类抽 1 个、漏检和误检共 12 个，看了前后 4 帧的画面。9 个和归类一致：切镜头的那拍发球是在侧面特写里打的；落地的确实落在近端球员脚边；回合结束后那次是球已经出界；轨迹丢失的那拍球被远端两人挡住。2 个误检看起来像远端的真击球，可能是 BFMD 漏标，也可能是我们的切镜头判断误报。1 个「远端」漏检，看不出是远端还是近端。所以上表只能看大致比例。「网前小球」只有 3 拍，是因为用地面标定去投影空中的球，位置会偏。这一类实际上多半被归进了「多人挨着球」和「远端」，不能当成网前没问题。

### 局限

- 只有职业男双的转播画面（高位后方机位、720p）。业余球馆的手机录像机位更低、画面更糊，不能直接套用这里的数字。
- 标注本身的误差没有单独估计。看起来一致地晚 1 帧以外，个别标注可能有 2–3 帧的偏差，±3 帧口径下会把一部分对的算成错的。
- 回合的起止用的是 BFMD 的 `Rally` 标签。实际使用时回合要自己切，切不准还会再损失一些。
